## 1. 项目是什么

### 1.1 一句话定位

面向盲人室内导航的 **Spatial Agent 最小原型**。它不是一个聊天机器人，而是一个具备

> **空间状态感知 → 多模态理解 → 任务规划 → 风险判断 → 行动决策 → 人机协同**

完整闭环的智能体。

### 1.2 系统循环（与机器人控制循环同构）

```
      感知 Perception
   （模拟器 / 未来真实硬件）
              ↓
   空间状态融合 Spatial State Fusion
              ↓
   SpatialState（Pydantic 结构化状态契约）
              ↓
   Agent Reasoning
   （实时多模态大模型 + 工具调用；不可用时规则引擎兜底）
              ↓
   Action Decision：SPEAK / CONTINUE / REPLAN / WAIT / ASK_USER
              ↓
   状态更新（用户是否被允许前进）→ 回到感知
```

### 1.3 阶段一的范围（明确不做的部分）

| 是 | 不是 |
| --- | --- |
| 模拟器产生空间/导航/传感器数据 | ❌ 不接真实 UWB / LiDAR / IMU 硬件 |
| **iPhone 摄像头是唯一真实输入源** | ❌ 不接真实 UE5 数字孪生 |
| 真实多模态大模型做决策（已跑通） | ❌ 语音播报只做日志输出，未接 TTS |
| 数据驱动的室内地图（改 YAML 即换地图） | ❌ 只实现单楼层（`floor` 字段已预留） |

## 4. 核心数据契约

### 4.1 `SpatialState`（系统内唯一状态契约）

```
SpatialState
├── timestamp: datetime
├── tick: int                        # 状态序号，每轮 +1
├── user: UserState                  # 来自 UWB（位置）+ IMU（朝向/速度）
│   ├── position: {x, y, floor}
│   ├── heading: float               # 0°=正北(+y)，顺时针为正，自动归一化到 [0,360)
│   ├── speed: float                 # m/s，>= 0
│   └── walking_status: Enum         # standing/moving/slowing/blocked/paused/arrived
├── navigation: NavigationState       # 来自路径规划器
│   ├── destination, current_route
│   ├── next_instruction, distance_to_goal, route_progress
│   ├── current_landmark, off_route
├── environment: EnvironmentState     # 来自 LiDAR / 超声
│   ├── front_clear, front_distance, corridor_width, narrow_passage
│   ├── left_obstacle, right_obstacle
│   └── obstacles: [Obstacle]        # 带 direction（6 方位）与 distance
├── semantic_scene: SemanticScene     # 来自地图语义层
│   └── objects: [str], summary
├── camera: CameraState               # 来自 iPhone / 浏览器
│   └── image_available, age_s, source, frame_id
├── risk: RiskState                   # 融合层计算
│   └── level: low/medium/high/critical, reason
└── confidence: ConfidenceState
    └── localization, perception
```

**关键设计：`model_config = ConfigDict(extra="forbid")`**
任何多余字段直接报错，杜绝"悄悄多出一个字段、下游拿不到"的隐性 bug。

**关键设计：`@model_validator(mode="after")` 自洽性校验**
例如 `front_distance` 必须等于正前方锥形区域内障碍的最近距离，否则**当场抛错**，
而不是让错误状态悄悄流到模型层（模型面对矛盾数据会给出荒谬决策，且极难排查）。

**关键设计：`to_prompt_dict()` 精简视图**
只保留决策必需字段并四舍五入，降低 token 消耗与数值噪声。

## 5. 具体怎么做的（关键实现与设计取舍）

### 5.1 状态融合：所有数据先归一化，模型只看结构化状态

`simulator/` 产出的是"原始感知"，`spatial/state_manager.py` 是**唯一**把它们变成
`SpatialState` 的地方。融合层负责：坐标系统一、方位判定（6 个方位）、
前方锥形区域最近距离、风险等级、置信度。

**为什么这么做**：把"数据清洗与几何计算"集中在融合层，Agent 层就只需要读字段。
换硬件时（UWB → LiDAR），改动被隔离在融合层的输入侧。

**事件顺序固定为**：障碍先更新 → 融合状态 → Agent 决策 → 用户按"是否允许前进"移动。
顺序错会导致 Agent 对着上一帧的环境做决策（这类 bug 极难查，所以写死在 `step()` 里）。

### 5.2 A\* 寻路：必须带安全间隙，且禁止对角穿角

栅格精度 0.25m，但规划出的路径要求与墙体保持 `path_clearance_m = 0.45m` 间隙。

**为什么**：纯栅格 A\* 会贴着墙角走。对盲人用户来说，"贴着墙走"意味着盲杖频繁撞墙、
或者直接切墙角撞上去。**同时禁止对角穿角**——两个对角方向都是墙时不允许斜穿，
否则路径会从墙角"挤"过去，实际物理上过不去。

`replan_deviation_m = 1.0`：偏离已规划路径超过 1m 就重规划，避免死板跟踪旧路径。

### 5.3 双引擎决策：模型为主，规则兜底，安全底线一票否决

```
SpatialState
    ↓
规则引擎 decide()  ──→ rule_action
    ↓
大模型 decide()   ──→ llm_action（可用时）
    ↓
_merge_with_safety()  ← ★安全底线在这里一票否决★
    ↓
最终 Action（source 字段标明这一轮谁做主）
```

- **规则引擎始终运行**：它同时是"兜底方案"和"安全底线"。
- **模型不可用时**（无 Key / 网络失败 / 输出非法 JSON / 熔断中）自动降级，**source 变为 `rule`**。
- **安全底线覆盖**：规则判定"立即停下"（`WAIT`）时，即使模型建议继续前进也会被覆盖。
  这是能放心让大模型参与安全关键决策的前提。自检 #22 专门验证这条。

### 5.4 工具层：副作用的唯一出口

`SPEAK` / `ASK_USER` / `REPLAN` 都不直接执行，而是转成 `tools.call("speak", {...})`。

**为什么**：
1. 模型无法绕过参数校验（例如播报超过 40 字会被截断、非法参数被拒）；
2. 所有副作用统一记账（`call_log` / `utterance_log`），便于审计与测试；
3. 规则决策也走同一条路，**行为一致性有保证**——不会出现"规则模式下不走工具层"的分叉。

### 5.5 多模态消息构造：图片 + 结构化状态 + 工具 schema 一起下发

一轮请求的组成：
1. **系统提示词**：角色、安全准则、输出格式（要求返回 JSON）
2. **结构化状态**：`to_prompt_dict()` 的精简视图（不是全量 `SpatialState`）
3. **图片**：`image_url` part，base64 内联（`latest_bytes()` 保证**过期帧不会送模型**）
4. **8 个工具 schema**
5. **历史记忆**：最近 30 轮

**输出解析带容错**：模型返回的 JSON 可能带 markdown 代码块、前后有解释文字，
`prompt_template.py` 做了提取与校验；校验失败则丢弃该决策并降级到规则（**绝不让非法输出影响安全**）。

### 5.6 熔断保护：让"Key 失效"不再烧配额

`LLMClient` 遇到不可自愈的错误会**熔断**一段时间，期间不再发起真实请求：

| 错误类型 | 冷却时长 | 理由 |
| --- | --- | --- |
| 认证失败 401/403 | **600s** | 不会自愈，等人工修 Key |
| 接口/模型名错误 404 | **600s** | 同理 |
| 限流 429 | 30s | 歇一会儿再试 |
| 网络异常 | 15s | 短暂退避 |

**注意用的是 `LLMClient.usable`（= 有 key 且未熔断），而不是 `available`。**
这是踩过的坑：只看 `available` 会导致 Key 失效时 1 Hz 无限重试，日志被刷爆且实时性归零。
成功一次即自动解除熔断。

### 5.7 摄像头链路：三段延迟，两个语义相反的取帧方法

**上行链路**：iPhone 采集 → JPEG 编码（640×480，质量 0.5）→ WebSocket 二进制帧
→ 服务端节流 → OpenCV 预处理（缩放最长边 768）→ 内存最新帧。

**端到端延迟 = 手机出帧间隔 + 服务端处理 + 网页刷新间隔**，三段各自可调：

| 环节 | 位置 | 当前值 | 备注 |
| --- | --- | --- | --- |
| ① 手机出帧 | iOS App 帧率选择器 | **5.0 fps** | **主要瓶颈就在这一项** |
| ② 上行限速 | `camera.max_fps` | **8**（客户端 5 fps） | 必须留余量，见第 7 节 |
| ③ 网页刷新 | `FRAME_REFRESH_MS` | **250 ms** | 与元数据轮询**分开**的独立定时器 |

**★ 两个取帧方法语义相反，绝不可合并 ★**

| 方法 | 用途 | 帧过期时 |
| --- | --- | --- |
| `latest_bytes()` | 喂多模态模型 | **必须返回 `None`** —— 否则模型对着"过去的画面"做安全决策 |
| `preview_bytes()` | 给前端预览 | **要能返回** —— 用户才能区分"从没收到画面"和"推流断了，最后看到的是这张" |

**★ 网页画面显示是三条互斥路径 ★**（优先级从高到低）

| 路径 | 触发 | 显示 |
| --- | --- | --- |
| 本机浏览器推流 | 点「开启摄像头推流」 | `<video>` + LIVE 角标 |
| **服务端画面** | 服务端有新鲜帧（iPhone App / 上传） | 画面 + 「服务端画面 · X.Xs 前」 |
| 空态 | 没有任何帧 | 「尚未注入画面」 |

由 `showVideoPreview / showServerPreview / showEmptyPreview` 统一切换。
**高频刷新只换 `<img>.src`，绝不改显隐状态**——它不知道服务端还有没有帧，
越权改状态会让推流中断时画面反复闪现（显隐只由慢速的 `refreshServerPreview` 管）。

### 5.8 配置驱动：地图是数据，不是代码

`config/config.yaml` 里换掉 `zones` / `route_landmarks` / `static_objects` 就换了整个环境，
**一行代码都不用改**。坐标系约定：x 向东、y 向北；`heading 0° = +y`，顺时针为正。

**阻挡型 vs 语义型物体**是重要区分：

| 类型 | `blocking` | 效果 |
| --- | --- | --- |
| 物理障碍（桌子、椅子） | `true` | 写入占用栅格，A\* **必须绕开** |
| 语义地标（门、路人） | `false` | 只进 `semantic_scene` 供模型理解，**不挡路** |

### 5.9 包导入用惰性导出（PEP 562）

`simulator/` 与 `spatial/` 存在互相引用，直接 `__init__.py` 里 import 会触发循环导入。
因此包的 `__init__.py` 采用 PEP 562 的模块级 `__getattr__` 惰性导出。

### 6.1 自检为什么要"离线、确定、快速"

`tests/selftest.py` 的 `base_cfg()` **默认清空 `llm.api_key`**。这是刻意的：
否则 `.env` 一配上真 Key，600 轮稳定性测试就会每轮发真实请求，
跑成分钟级并被误判为"卡死"（**踩过这个坑**）。

### 6.2 写 UI 断言的纪律

**不要依赖运行时状态。** 例：测试页对 `CONTINUE` 有防刷屏逻辑（不追加行动流），
所以"feed 非空"这类断言会随 Agent 当前状态时通时不通。
正确做法是**分别钉死两条路径**（`CONTINUE` 必须抑制 + 非 `CONTINUE` 必须插入），
用例才确定。（29/29 时踩过，已修。）

## 7. 已踩过的坑（交接必读，这部分最省时间）

| # | 坑 | 症状 | 根因 | 修法 |
| --- | --- | --- | --- | --- |
| 1 | **百炼 Key 套餐与 Base URL 必须配套** | 401，报错长得像「Key 无效」，极易误判成 Key 复制错 | `sk-`/`sk-sp-`/`sk-ws-` 三类套餐各绑不同 Base URL，混用一律 401 | 按前缀自动配对；工具 `tools/set_llm_key.py` 一键修 |
| 2 | **前缀必须小写** | 地址对也 401 | `Sk-sp-` ≠ `sk-sp-` | 归一化时自动纠正首段大小写 |
| 3 | 曾被误判为「ECDSA 签名令牌」 | —— | 对 Key 末段做 base64/DER 结构分析得出错误结论 | **教训：先查前缀语义，不要先做密码学分析**。套餐 Key 天然含点号，是合法格式 |
| 4 | **`max_fps` 与客户端帧率同档会放大丢帧** | 5 fps 客户端实测只有 3 fps | 节流判据 `now - _last_accept < 1/max_fps`，而 `_last_accept` **只在帧被接受时更新**；一次微小负抖动就丢帧，下一帧要等 0.398s | `max_fps=8` 留余量。**A/B 实测：留余量 40/40 接受、0 节流；不留余量 25/40 接受、15 节流（有效 62%）** |
| 5 | **网页只显示"本机浏览器"的画面** | 手机推流时网页一片黑、写着「尚未注入画面」，误判成摄像头坏了 | 面板只认本机浏览器注入，**没有任何渲染服务端帧的路径** | 新增 `GET /api/frame` + 三条互斥显示路径；面板改名「摄像头画面」 |
| 6 | **`latest_bytes` 不能直接用于预览** | —— | 它过期返回 `None`（喂模型必须如此），前端拿不到"最后一张" | 另开 `preview_bytes(max_age_s)`，语义相反 |
| 7 | **局域网 IP 打印成 VPN 虚拟地址** | 打印 `198.18.0.1`，用户填进手机必然连不上，且完全看不出哪里错 | UDP 选路选中了隧道网卡 | 排除基准测试网段 `198.18.0.0/15` + 三层探测 |
| 8 | **`xcodebuild` 读不到 Xcode 的账号** | `No Accounts` / `No profiles for ...`，即使证书和团队都在 | Xcode 把账号放在自己进程/钥匙串里，CLI 读不到（`DVTDeveloperAccountManagerAppleIDLists` 为空但 `IDEProvisioningTeamByIdentifier` 有团队） | 需在 Xcode 里**手动 ⌘R 一次**生成描述文件，之后 CLI 才能接管 |
| 9 | **设备标识用错** | `xcodebuild` "找不到目标"，**静默不产出 `.app`** | `-destination` 要 UDID（`00008150-…`），填的却是 devicectl 内部标识（`8B7EEE49-…`） | 从 `-showdestinations` 自动探测 UDID |
| 10 | **首次安装必须走 USB** | `developer disk image could not be mounted` | 纯 Wi-Fi 连接（`localNetwork`）枚举不到设备 | 插 USB（`wired`）；手机锁屏时构建还会白等 60s |
| 11 | **`HTTP_PROXY` 让本机请求被 502** | 连 `127.0.0.1` 的客户端失败 | 代理把回环请求也拦了 | 所有本机客户端显式禁代理 / 设 `NO_PROXY` |
| 12 | **Pydantic 状态字段当方法调用** | 多模态**静默失效**，极难查 | 写成 `state.navigation.current_route()`（它是 list 不是方法） | 异常被主循环兜底 except 吞掉 → 现已修正 |
| 13 | **后台服务被回收** | 服务无故消失、端口无监听 | `nohup … &` 起的进程会被回收 | 用长期前台进程；**要长期占服务必须在用户自己的终端里跑** |
| 14 | **从噪声里提取模型的特定回答** | 无法区分"目标回答"和 Agent 的状态播报 | 用时间窗/长度启发式不可靠 | **强制模型用固定前缀作答**（如 `我看到：`），确定性摘取 |
| 15 | **本机 Bash 的 `grep` 不可靠** | 对确定存在的字符串也返回空 | 环境问题 | 文件内容检索用 ripgrep / Read，不用 `grep` 命令行 |

## 9. 优化机会（按优先级，含实测依据）

### 9.1 【P0】把主循环从 0.49 Hz 提到 1.0 Hz

**实测依据**

```
墙钟经过      : 12.1 s
tick 增加     : 6      → 实际循环频率 0.49 Hz（配置 tick_hz = 1.0）
模拟时钟增加  : 6.0 s  → 模拟/真实时间比 0.49×
```

**根因**：`run_loop()` 里 `system.step()` 是**同步阻塞**调用，而 `step()` 内部同步等待
大模型返回（`kimi-k2.5` 含图 + 状态 + 8 工具 schema ≈ **1.9s**）。
于是每轮耗时 1.9s，但只推进 1.0s 模拟时间 → 循环频率腰斩、仿真时间比真实时间慢一半。

```python
# api/websocket_server.py 当前实现
await asyncio.to_thread(system.step, next_t)          # ← 在这里同步等模型
await asyncio.sleep(max(0.0, next_t - elapsed))       # 已超时，实际 sleep(0)
```

**优化方案（三选一，按侵入性排序）**

| 方案 | 做法 | 预期收益 | 风险 |
| --- | --- | --- | --- |
| **A. 决策异步化 + 结果复用**（推荐） | 感知/融合仍按 1Hz 跑；模型决策异步发起，**用"上一次的决策"驱动本轮**（决策滞后一拍） | 循环恢复到 1.0Hz；模型仍在环内 | 决策滞后 1 拍（对 1 m/s 的行人 ≈ 1m 位移，需评估安全影响） |
| **B. 缩短模型延迟** | 降低图片边长（768→512）、精简工具 schema、换更快的模型 | 延迟可能降到 ~1.0s | 需重新验证视觉准确率 |
| **C. 规则预筛 + 模型复核** | 只在"风险 ≥ medium"或"规则不确定"时才调模型 | 调用次数大幅下降 | 改变了"模型始终在环"的架构语义 |

**验证方式**：改完重跑第 9.1 节的测量脚本，`实际循环频率` 应 ≥ 0.9 Hz。

### 9.2 【P0】把视觉结果回灌到结构化状态（阶段二核心）

**现状**：模型能"看见"并描述柜子/置物架，但这些信息**没有进入
`SpatialState.environment.obstacles`**，因此：
- A\* 路径规划**看不见它们**；
- 规则引擎的临界风险判定**也用不上它们**；
- 视觉只影响"模型说的话"，不影响"系统的安全判断"。

**优化方案**：增加一个「视觉 → 结构化障碍」的转换环节：

```
JPEG 帧 ──→ 视觉障碍检测（多模态模型 / 端侧检测器 / LiDAR 深度）
        ──→ 障碍列表（相对方位 + 估计距离）
        ──→ 并入 EnvironmentState.obstacles
        ──→ 同时喂给 A* 与规则引擎
```

**为什么这是最高价值的一条**：它把"视觉"从**描述层**提升到**决策层**，
让 `SpatialState` 真正成为"融合了全部感知的唯一真相"——这正是架构约束 #1 的完整形态。

**注意**：需处理视觉距离估计误差，建议给视觉障碍**较低的置信度**并只用于"减速/提醒"，
不直接用于"紧急停止"（除非与 LiDAR 一致）。

### 9.3 【P1】决策延迟与安全性的平衡

`min_interval_s = 4.0`（语音最小间隔）+ 决策滞后，共同决定"危险出现到用户被提醒"的延迟。
建议加一条**端到端安全延迟**指标：从"障碍进入 critical 距离"到"用户收到 `WAIT`"的耗时，
并纳入自检。当前估算 ≈ 1.9s（模型延迟）+ 节拍误差，**对 1 m/s 的行人约等于 2m 位移**，
偏高，值得专门优化。

### 9.4 【P1】测试体系升级

- 把 1191 行手写 runner 迁移到 **pytest**，可获：fixture 复用、`parametrize`、
  `pytest-cov` 覆盖率、`-k` 选择性运行、IDE 内单点调试。
- 给"踩过的坑"逐条补**回归测试**（目前部分只写在文档里）：
  例如 `max_fps` 余量、`preview_bytes` 过期语义、局域网 IP 过滤规则。

| --- | --- | --- |

### 11.2 交接注意

1. **`.env` 不进版本库**（已在 `.gitignore`）。交付包**不含 `.env`**，
   接收方需 `cp .env.example .env` 后自行填 Key。用 `tools/set_llm_key.py` 最省事。
2. **Key 与 Base URL 必须配套**（见第 7 节 #1）。交付文档不包含任何真实密钥。
3. 本机若设了 `HTTP_PROXY`，所有连 `127.0.0.1` 的操作都要显式绕过代理。
4. 改完 `.py` **必须重启 `--serve`**（不热加载）。
5. 改完 `api/test_page.html` **必须跑 `tools/ui_smoke_test.py`**。
6. 改完摄像头链路**必须跑 `tools/e2e_test.py`**。
7. 自检必须保持**离线**：`base_cfg()` 里 `llm.api_key` 要清空（见 6.1）。

### 11.3 交付包内容与安全边界

交付 zip 由 `scripts/package.py` 生成，顶层自带 `BlindSpatialAgent-v<版本>/` 目录，解压不散落。
**它只含源码、文档与工具，不含任何可运行环境**：

| 排除项 | 原因 |
|---|---|
| `.env` | ★含真实 API Key，绝不出包★（脚本会复查并删档失败） |
| `.venv/` | 虚拟环境，由 `requirements.txt` 重建 |
| `ios/_device_backups/` | ★设备 App 容器备份（12MB，含偏好与截图缓存），隐私风险★ |
| `ios/**/build*` | Xcode 派生数据（本机实测 450MB） |
| `**/xcuserdata/` | Xcode 个人界面状态，与使用者绑定 |
| `logs/` | 运行日志与抓拍图，含用户真实画面 |
| `__pycache__/ *.pyc *.log .DS_Store` | 缓存与临时文件 |

接收方首次使用顺序：
```bash
unzip BlindSpatialAgent-v*.zip && cd BlindSpatialAgent-v*
python -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env                 # 填自己的 Key
python main.py --selftest            # 应为 40/40 全绿（离线，不需要 Key）
python main.py --serve               # 打开 http://127.0.0.1:8000/
```
