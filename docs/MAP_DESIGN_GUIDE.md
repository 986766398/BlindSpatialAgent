# 地图设计指南（`config/config.yaml` → `simulator.map`）

> 这份文档只回答一件事：**怎么改地图，以及改完怎么确认没改坏。**
> 地图是**数据驱动**的 —— 换一个楼层通常只需要改 `config.yaml`，代码零改动。
> 但数据驱动最大的风险是「静默故障」：加一件家具把房间门堵死，A\* **不会报错**，
> 只会找不到路，然后智能体在原地打转。所以本文第 4 节（验证）是必读的。

---

## 1. 地图由四组数据构成

| 键 | 含义 | 是否物理挡路 |
|---|---|---|
| `zones` | 可通行区域的**矩形并集**。矩形之外的一切都是墙。含房间、走廊、**门洞** | 是（栅格的唯一来源） |
| `route_landmarks` | 全局路线点（NavMesh 风格的骨架）：入口 → 大厅 → 南走廊 → 办公区 → 北走廊 → 卫生间 | 否（仅导航骨架） |
| `static_objects` | 圆形静态物体：桌 / 椅 / 沙发 / 箱子 / 门 / 路人 / 空调 | 由 `blocking` 决定 |
| `area_objects` | **区域型（矩形）障碍**：施工围挡 / 储物柜墙 / 沙发组 / 工位岛 … | 由 `blocking` 决定 |

坐标约定：**x 向东、y 向北；heading 0° = +y，顺时针为正。**
栅格精度 `grid_resolution_m`（默认 0.25m）决定一切几何精度。

---

## 2. 门洞（`zones` 里以「门 / 门口」结尾的矩形）

房间与走廊之间留一条 **1m 厚的墙带**，墙上只在门洞处开口 ——
门洞就是一条 1m 厚、2~3m 宽的矩形，写进 `zones` 里。

```yaml
- {name: "卫生间门口", x_min: 10.2, x_max: 12.8, y_min: 38.0, y_max: 39.0}
```

设计要点：

1. **门必须与房间、走廊各有 1 条边贴合**（edge-adjacent）——只在角上碰到不算，
   人是走不过去的。`tests/selftest.py` 用例 75 会检查这一点。
2. **宽度按"扣掉安全间隙后还能过"来定**。寻路时会以 `motion.path_clearance_m`
   （默认 0.45m）把墙向外膨胀，所以：
   `有效通行宽度 ≈ 门宽 − 2 × 0.45m`。门宽 2.6m → 有效约 1.7m（栅格口径 2.0m）。
3. ★**门只开在房间的一面墙上**★。卫生间门在南墙，站在房间里往西推就是**撞墙**，
   不是「地图没门」。看小地图上的橙色门洞标记确认方向。
4. 若房间被改小/挪动，**门洞坐标要跟着改**，否则门会悬在墙上（贴合判定失败）。

## 3. 区域型障碍（`area_objects`）

```yaml
area_objects:
  - {type: "cordon", x_min: 23.5, x_max: 30.5, y_min: 8.4, y_max: 9.9, blocking: true}
```

写 `x_min/x_max/y_min/y_max`，框架自动换算成「中心 + 半宽半高」，
对外与圆形物体**共用同一套结构**（`MapObjectInfo.hx/hy`）。

**为什么需要它**：6m×1m 的施工围挡如果按圆形近似，会变成半径 3m 的大圆 ——
走廊中间凭空多出一堵圆墙，而且用户贴着围挡走时系统还报「距离 3 米」。
矩形障碍在占用栅格、避障距离、语义场景、前端小地图里全程按矩形处理。

**放之前先算清楚「剩下多宽能走」**：可通行净宽必须 **> 2 × path_clearance_m**，
否则那条通道会实际上被封死（`orphan_ratio` 与用例 75 会抓出来）。

## 4. 改完地图必做的三步验证

```bash
# ① 画一张图先肉眼看（最快发现"绕得要死但还能过"）
.venv/bin/python tools/render_map.py     # 输出 docs/map_check.png

# ② 连通性体检（直接打印房间可达性 / 门宽 / 孤岛占比）
.venv/bin/python -c "
from config.loader import load_config
from simulator.map_simulator import MapSimulator
m = MapSimulator(load_config()); r = m.connectivity_report()
print('房间可达:', r['rooms']); print('门宽:', r['doors']); print('孤岛:', r['orphan_ratio'])
"

# ③ 全套自检（用例 75 就是这件事的固化版，几分钟内跑完）
.venv/bin/python main.py --selftest

# ④ 关键路径实跑：能不能真的走到目的地（验收 S09 / 七拍 Demo 都覆盖）
.venv/bin/python main.py --acceptance
.venv/bin/python main.py --acceptance-demo
```

> ★第 ① 步不是可选项★ 用例 75 只能抓「房间不可达 / 门洞被封死」这类**硬故障**，
> 抓不住「处处能过但处处要绕」——而后者才是用户抱怨"障碍太多、一直在重规划"的成因。
> 摆完障碍先看图，比跑测试更快看出"这条路被切成锯齿了"。

`connectivity_report()` 返回四个口径：

| 字段 | 含义 | 期望 |
|---|---|---|
| `rooms` | 每个房间型区域能否从起点走到 | 全 `True` |
| `doors` | 每个门洞在**寻路栅格**上的有效通行宽度（m） | ≥ `max(1.0, 2×clearance)` |
| `orphan_ratio` | 与主可通行区域脱开的「孤岛」占比 | `< 0.01` |
| `free_cells` | 可通行格总数（可通行比例 = 它 / 全部格） | 0.05 ~ 0.95 |

## 5. 已知陷阱（踩过的，别再踩）

1. ★**中央通行带 x∈[18,22] 不要摆新障碍**★。
   验收 Demo 第 2 拍要求「12 秒直行 > 6m 且不刷屏」，主干道上放障碍会把它
   变成「边走边绕」，直接测坏直行剧本。新障碍请放在走廊两翼或办公区两侧。
2. ★**`route_landmarks` 的顺序与个数被测试依赖**★。
   用例 7 取 `landmarks[2]` 与 `landmarks[3]` 之间的路段并要求 1m 内必须有门洞；
   用例 4/5/6 取 `landmarks[-1]` 作终点。**不要在中间插入或重排路点**，
   要加就加在末尾（并同步改终点语义）。
3. ★**`destination` 必须是一个存在的路点名**★（当前为 `卫生间`），
   否则「带我去 X」无法解析。
4. ★**`zones` 的顺序有语义**★：`zone_at()` 返回**第一个**命中的区域。
   起点 `(20, 4.5)` 落在 `入口大厅` 上，测试依赖这一点，别把新区域插到它前面。
5. **`blocking: false` 的物体只进语义场景**（门 / 路人 / 壁挂空调），
   不参与避障与寻路 —— 用来丰富「旁边有什么」的描述，不会挡路。
6. **改完地图不是只跑自检就完事**：`--acceptance`（S09 全程到达）与
   `--acceptance-demo`（第 2 拍直行）才真正回答「用户还能不能用」。
7. ★**障碍密度本身就是一条验收项**★。
   静态障碍不会过期、区域障碍是一整片，摆多了的后果不是"走不过去"（用例 75 照样全绿），
   而是**每走两步就被迫绕行/减速**，用户听到的是
   「为您重新规划路线」「前面有障碍」「请停下」——听起来像系统坏了。
   当前口径：**区域障碍 4 处以内、主干道外的点状障碍 4 个以内**；
   `simulator.obstacles`（动态）用 `max_active=2 / spawn_interval_s=10`。
   要知道自己摆得算不算多，跑一次 `python main.py --ticks 120 --no-llm/brief` 数一下
   `WAIT / REPLAN / ASK_USER` 出现了几次。**加障碍前先减一个**。
8. ★**`area_objects` 只用来表达"一整片"的障碍**★（围挡 / 柜墙 / 沙发组 / 工位岛）。
   能用圆形说清楚的东西（垃圾桶、纸箱、椅子）就留在 `static_objects` 里 ——
   矩形会连带把整片可通行区域挖掉，用它"顺手加几个障碍"很容易把走廊切碎。
